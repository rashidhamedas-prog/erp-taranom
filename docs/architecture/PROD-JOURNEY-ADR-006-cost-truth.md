# ADR-006 — مسیر سفارش تا رسید انبار: بهای واقعی + لای مشترک + R13

**وضعیت:** Accepted (موج‌های پیاده‌سازی)  
**تاریخ:** ۱۴۰۵/۰۷/۲۷  
**عمق:** کامل (skill-top)  
**زمینه:** بازطراحی بر اساس درس‌های v427–v469 + خواستهٔ مالک (سفارش ۱/N محصول، لای مشترک، بها تا انبار)

ADR-001…005 و قوانین R1–R13 عوض نمی‌شوند؛ این سند شکاف **مسیر عملیاتی + تسهیم قابل‌انتخاب + قفل بها** را می‌بندد.

---

## ۱) مدل ذهنی قفل‌شده

```
BOM (هر محصول مستقل)
  → سفارش تولید (۱ یا چند محصول اصلی؛ fg_plan جدا)
    → لایه‌چینی / مارکر (تک‌محصول کلاسیک یا چندمحصول مشترک)
      → گیت: قبل از عبور از مرحلهٔ برش، لای کامل + مصرف/ضایعات/انحراف ثبت شده
        → بقیهٔ مراحل مسیر (مشترک / اختصاصی)
          → پک / رسید محصول (اینجا بهای واحد «رسمی» می‌شود)
            → ورود انبار FG
```

- BOM همیشه per-product است؛ چندمحصولی بودن فقط در **سفارش و لای/مراحل** معنا دارد.
- هر رویداد مؤثر (مواد، ضایعات ۵۲۲۱، دستمزد، سربار جذب، پیمانکار، …) تا قبل از رسید در WIP همان سفارش می‌ماند.
- `cost_final=true` فقط وقتی لای (در صورت نیاز پارچهٔ متری) + مسیر لازم + رسید/پک کامل باشد — WIP متوازن ≠ بهای نهایی (درس v467).

---

## ۲) تسهیم هزینهٔ لای مشترک (پاسخ سؤال ۱ مالک)

روی هر `cutting_batches` فیلد **`allocation_basis`**:

| مقدار | معنی | وزن فنی |
|--------|------|---------|
| `pieces` | نسبت تعداد قطعه در مارکر (پیش‌فرض) | `pieces_per_ply` |
| `fabric` | نسبت مصرف پارچهٔ استاندارد/اعلام‌شده | `fabric_std_m × pieces_per_ply` |
| `manual` | درصد دستی کاربر (جمع ۱۰۰٪) | `weight` اجباری |
| `hybrid` | پیشنهاد ترکیبی سپس قابل‌ویرایش | میانگین نرمال‌شدهٔ pieces٪ و fabric٪؛ اگر کاربر weight بدهد همان دستی |

همهٔ حالت‌ها در UI قابل انتخاب‌اند. مبنای ذخیره‌شده روی `cutting_batch_allocations.basis` و سربرگ batch می‌ماند (ممیزی).

## ۳) بعد از ورود انبار — بهای تمام‌شده (پاسخ سؤال ۲، به زبان ساده)

**سؤال عامیانه:** وقتی لباس رفت انبار، اگر فهمیدیم لایه‌چینی یا هزینه اشتباه بوده، چه‌کار کنیم؟

**تصمیم قفل‌شده — «قفل رسمی + اصلاح شفاف»:**

1. **بهای واحد در رسید/پک رسمی است** (همان لحظهٔ ورود به انبار محصول).
2. **اگر هنوز چیزی فروخته نشده:** مسیر تمیز = ابطال رسید (و در صورت نیاز PACK) → اصلاح لایه/مرحله → رسید مجدد. موجودی و دفتر با R13 کامل برمی‌گردند.
3. **اگر بخشی فروخته شده:** بدون باز کردن کل خط تولید، **اصلاح اختلاف بها** مثل الگوی v466/v468: سهم مانده در انبار → بهای کالا؛ سهم فروش‌رفته → بهای تمام‌شده فروش. مراحل سفارش دوباره باز نمی‌شوند.
4. **ویرایش بی‌سند یا دستکاری خام میانگین بعد از فروش ممنوع است.**

این همان ترکیب تجربهٔ عملی ترنم است؛ نه «هر وقت خواستی عدد را عوض کن»، نه «تا ابد قفل مطلق بدون راه اصلاح».

## ۴) ویرایش / ابطال (R13)

| عملیات | ایجاد | ویرایش | ابطال |
|--------|:-----:|:------:|:-----:|
| لای تک‌محصول | ✅ | ✅ (پوشش‌شده با قواعد v466) | ✅ (v468) |
| لای چندمحصول (batch) | ✅ | موج ۲: reverse+repost (فعلاً void ثم ثبت مجدد؛ `E_SHARED_CUT_NO_AMEND` تا موج ۲) | ✅ voidSharedCut |
| خروجی مرحله / حواله | ✅ | طبق موتور پیشرفته | ✅ |
| رسید / finalize | ✅ | amend با قفل بخش ۳ | ✅ hollow/full reverse |

حذف فیزیکی ممنوع. همه در `db.transaction`.

### یافتهٔ ممیزی R13 (ادغام ۱۴۰۵/۰۷/۲۷)

منبع: ممیزی مسیر تولید + تحقیق شکاف هزینه.

- لای کلاسیک: create/edit/void تقریباً کامل؛ covered عمداً partial (v466/v468).
- لای shared: create+void؛ amend = `E_SHARED_CUT_NO_AMEND`؛ UI گاهی «ویرایش» نشان می‌دهد و toast رد می‌کند → در W2 یا amend واقعی یا حذف دکمه.
- `voidCuttingPackByLay` فقط یک pack (`LIMIT 1`) — برای چند PACK WIP مشترک خطرناک.
- `purge`/`reverseStage` بعد از `completed` با `E_ORDER_FINALIZED`؛ زنجیرهٔ کامل finalize→pack→lay در تست G1 هنوز PENDING.
- مدل داده: همچنان **یک BOM چندخروجی** روی یک سفارش (نه N BOM مستقل) — مگر مالک صریحاً W5 بخواهد.
- `test-sync` روی ویندوز Node ۲۴ به‌خاطر binding بهتر-sqlite3 بالا نمی‌آید؛ معیار سبز = ایران.
